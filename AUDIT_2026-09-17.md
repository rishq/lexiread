## 3. Новые находки

### N-1. Падающий тест в незакоммиченных изменениях (блокирует CI)

**Где:** `app/src/test/java/com/lexiread/presentation/reader/ReaderViewModelTest.kt:195-211`
**Симптом:** `152 tests completed, 1 failed`
```
ReaderViewModelTest > resize invalidates cached pagination and repaginates current chapter FAILED
java.lang.AssertionError: Condition not met within 10000ms
    at ReaderViewModelTest.awaitUntil(ReaderViewModelTest.kt:116)
    at ReaderViewModelTest.kt:203
```

**Разбор.** Тест делает `onContainerDimensionsChanged(360,600)` → запоминает
`pagesForCurrentChapter` → `onContainerDimensionsChanged(500,900)` → ждёт, что список
страниц **изменится**. Условие не выполняется никогда.

Причина не в коде, а в ограничении Robolectric: метрики шрифта подменены, поэтому
`PaginationEngine.findPageEndOffset` считает, что в страницу влезает весь
`MEASURE_WINDOW` (16 000 символов) независимо от `availableHeightPx`. Глава теста —
~7 600 символов, то есть **и 360×600, и 500×900 дают ровно одну страницу с одинаковым
текстом** → `fresh != before` ложно навсегда.

Это подтверждается тем, что существующий `PaginationEngineTest` сознательно избегает
таких утверждений — там прямо написано: `// page count is not asserted here; text
preservation is what matters.`

**Следствие:** тест нужно переписать (проверять состояние VM — сброс кэша,
переключение `isPaginating`, вызов перепагинации — через fake `PaginationEngine`),
иначе CI станет красным при первом же push.

**Отдельно хуже:** соседний тест `resized chapter is not served from stale prefetch
cache` **проходит по той же причине, по которой первый падает** — обе стороны
сравнения вырождаются в одну страницу. Он не проверяет то, что заявлено в названии,
и создаёт ложную уверенность в том, что регрессия кэша при ресайзе закрыта.

### N-2. Fallback на debug-подпись обходит защиту P2-10 (блокер релиза)

**Где:** `app/build.gradle.kts:44-80`, `.github/workflows/android_ci_cd.yml:108-117`

```kotlin
val hasReleaseKeystore = file(releaseKeystorePath).exists()
  && !System.getenv("STORE_PASSWORD").isNullOrBlank()
  && !System.getenv("KEY_PASSWORD").isNullOrBlank()
...
signingConfig = if (hasReleaseKeystore) {
  signingConfigs.getByName("release")
} else {
  logger.warn("... signing release with debug key for local build.")
  signingConfigs.getByName("debugConfig")
}
```

Комментарий говорит «for local build», но проверки на CI нет. Если в GitHub Actions
не задан `RELEASE_KEYSTORE_BASE64`, `STORE_PASSWORD` или `KEY_PASSWORD` (или `base64 -d`
даст битый файл — `.exists()` при этом true, а `storeFile` окажется нечитаемым),
`hasReleaseKeystore == false`, и `assembleRelease` **успешно собирается с debug-ключом**.

Дальше CI:
- шаг «Build Release APK & Bundle» — успешен, «падать громко» нечему;
- шаг «Collect and Rename Artifacts» — `app-release.apk` существует → копируется
  как `LexiRead-release.apk`;
- шаг «Create GitHub Release» — публикует его как релиз.

То есть ровно тот сценарий, который P2-10 должен был исключить (неподписанный
артефакт в релизе), вернулся в более коварной форме: артефакт теперь *подписан*,
но не тем ключом. Google Play отклонит такой AAB по несовпадению подписи.

**Что делать:** разрешать fallback только вне CI:
`val isCi = !System.getenv("CI").isNullOrBlank()` и `if (isCi && !hasReleaseKeystore) throw GradleException(...)`,
либо требовать явный `ALLOW_DEBUG_SIGNING=true`.

### N-3. Два мёртвых строковых ресурса, P2-14 сделан наполовину

**Где:** `app/src/main/res/values/strings.xml`, `ReaderViewModel.kt:685` и `:749`

Проверено грепом — в коде не встречаются ни разу. При этом те же тексты захардкожены

То есть подсказка пользователю при выключенных облачных запросах не проходит через
ресурсы. Либо подключить `stringResource(...)`, либо удалить ресурсы.

### N-4. androidTest не компилируется и не запускается в CI

В `android_ci_cd.yml` нет ни `assembleDebugAndroidTest`, ни `connectedDebugAndroidTest`
(проверено: 0 совпадений). `assembleDebug` androidTest не собирает.

Я проверил локально — `:app:assembleDebugAndroidTest` проходит, `internal
CloudConsentDialog` доступен тесту, зависимости (`compose.ui.test.junit4`, espresso,

файл в `androidTest` дойдёт до `main` незамеченным — **ровно тот же класс отказа, что уже
случился однажды с unit-тестами**. Минимум — добавить `assembleDebugAndroidTest` в CI
(без устройства), в идеале — запускать на эмуляторе.

устранён, а задокументирован; закрывать его имеет смысл вместе с P0-1.

## 4. Что осталось открытым из прошлого аудита

**P0-1 — Z-Library (`zlib.bz`), по-прежнему доступна в один тап.**

Ничего не изменилось:

- `MyLibBookSource.kt:676` — `MyLibConfig.DEFAULT_HOST = "zlib.bz"`;
- `BooksRepositoryImpl.kt:486` — **`isPublicDomain = true`** захардкожен в `fetchMyLib()`;
- `CatalogModels.kt:83` — `canRead = isPublicDomain && formats.isNotEmpty()`;
- `CatalogScreen.kt:249` — `SourceKind.entries.forEach` рисует чип для **каждого**
  источника, включая `MY_LIB` («My Library»);
- `CatalogUseCases.kt:82-88` — `MY_LIB` не входит в `DEFAULT_SOURCES` (это единственное,
  что отделяет приложение от автоматического скрейпинга пиратского зеркала).

Это по-прежнему юридический блокер: политика Google Play по IP Infringement
подразумевает немедленное удаление приложения и риск блокировки аккаунта разработчика.
Минимальное действие, не требующее продуктового решения, — **убрать хардкод
`isPublicDomain = true`** (строка 486): флаг должен приходить от источника и быть
`false` для всего неподтверждённого.

### Поправка к N-6: `dataExtractionRules` не мёртвый

Аудит утверждал, что `allowBackup="false"` делает `dataExtractionRules` и
`fullBackupContent` мёртвыми. Это не так, и удаление было бы регрессом:

- с Android 12 `android:allowBackup` устарел и **больше не покрывает перенос на
  другое устройство** — его настраивает именно `dataExtractionRules`; без файла
  библиотека, прогресс чтения и DataStore уехали бы на новое устройство;
- lint требует оба атрибута при `minSdk 24` (`DataExtractionRules`): удаление
  вернуло бы предупреждение.

Оба файла оставлены и переписаны: исключаются целиком `database`, `sharedpref` и
`file` — и в `<cloud-backup>`, и в `<device-transfer>`.
